
# Sauvegarde automatique des namespaces Kubernetes avec NetBackup 11.2

## 1. Objet du document

Ce document décrit le principe de mise en place d'une sauvegarde automatique des namespaces Kubernetes/OpenShift avec **Veritas NetBackup 11.2**.

L'objectif est de mettre en place un modèle industrialisé dans lequel :

- les namespaces Kubernetes sont identifiés automatiquement ;
- leur niveau de protection est déterminé par des **labels Kubernetes** ;
- les **Intelligent Groups NetBackup** sélectionnent dynamiquement les namespaces ;
- les **Protection Plans** définissent les règles de sauvegarde ;
- les **SLP (Storage Lifecycle Policies)** assurent le cycle de vie des copies ;
- plusieurs niveaux de protection sont proposés, de **Bronze à Platinum** ;
- le niveau Platinum permet de disposer d'une copie supplémentaire sur un **site Bunker** ;
- la réplication vers le Bunker est réalisée via **AIR (Auto Image Replication)** ;
- le réseau entre la production et le Bunker peut rester fermé hors des fenêtres de synchronisation.

L'objectif est de séparer clairement :

> **la demande de protection exprimée dans Kubernetes**

de

> **la manière dont NetBackup réalise techniquement cette protection.**

---

# 2. Architecture cible

L'architecture cible repose sur deux domaines NetBackup :

- un domaine **NetBackup Production** ;
- un domaine **NetBackup Bunker**.

Le domaine Production protège les workloads Kubernetes/OpenShift et stocke les sauvegardes sur le Data Domain de production.

Le domaine Bunker possède son propre serveur Primary NetBackup et son propre Data Domain. Les images destinées au Bunker sont transférées par **AIR** lorsque la connectivité réseau entre les deux sites est disponible.

# 3. Principes d'architecture

L'architecture repose sur quatre niveaux de responsabilité.

| Composant | Responsabilité |
|---|---|
| Kubernetes/OpenShift | Déclare le niveau de protection souhaité |
| Intelligent Group | Sélectionne automatiquement les namespaces |
| Protection Plan | Définit la politique de protection |
| SLP | Orchestration des copies et du cycle de vie |

Le namespace Kubernetes ne connaît donc pas les détails d'infrastructure tels que :

- le nom du Data Domain ;
- le Storage Unit ;
- le SLP ;
- le serveur NetBackup ;
- le site Bunker.

Ces éléments sont administrés dans NetBackup.

```text
   |
GOLD
```

La classification peut évoluer en fonction des exigences RPO/RTO, de la criticité applicative et des exigences de résilience.

# 5. Labels Kubernetes

Le niveau de protection est porté par un label Kubernetes.

Exemple :

```yaml
metadata:
  labels:
    backup-enabled: "true"
    backup-tier: "platinum"
    environment: "production"
```

Pour un namespace Gold :

```yaml
metadata:
  labels:
    backup-enabled: "true"
    backup-tier: "gold"
    environment: "production"
```

Pour un namespace Silver :

```yaml
metadata:
  labels:
    backup-enabled: "true"
    backup-tier: "silver"
    environment: "production"
```

Pour un namespace Bronze :

```yaml
metadata:
  labels:
    backup-enabled: "true"
    backup-tier: "bronze"
    environment: "development"
```

## 5.1 Principe de découplage

Il est recommandé de ne pas mettre directement le nom du stockage dans le label.

### À éviter

```yaml
labels:
  backup-storage: "DD-PROD-01"
```

### À privilégier

```yaml
labels:
  backup-tier: "gold"
```

Le label décrit une **exigence de service**, et non une implémentation technique.

Ainsi, si le Data Domain utilisé par le niveau Gold change, aucune modification des namespaces Kubernetes n'est nécessaire.

# 6. Intelligent Groups

Les Intelligent Groups permettent de sélectionner automatiquement les assets Kubernetes correspondant à des critères définis.

NetBackup permet notamment d'utiliser des **conditions basées sur les labels** pour construire les groupes intelligents Kubernetes.

Le modèle proposé est :

```text
IG-K8S-BRONZE
IG-K8S-SILVER
IG-K8S-GOLD
IG-K8S-PLATINUM
```

## 6.1 Intelligent Group Bronze

Condition logique :

```text
backup-enabled = true
AND
backup-tier = bronze
```

## 6.2 Intelligent Group Silver

```text
backup-enabled = true
AND
backup-tier = silver
```

## 6.3 Intelligent Group Gold

```text
backup-enabled = true
AND
backup-tier = gold
```

## 6.4 Intelligent Group Platinum

```text
backup-enabled = true
AND
backup-tier = platinum
```

Le fonctionnement est dynamique : un namespace qui reçoit le label correspondant entre dans le périmètre de l'Intelligent Group lorsque le Protection Plan s'exécute.

Le modèle cible est :

# 9. Matrice des niveaux de protection

Les valeurs ci-dessous constituent une **proposition de conception**. Les RPO, rétentions et fenêtres devront être ajustés aux exigences réelles.

| Niveau | Label | Fréquence indicative | Rétention indicative | Stockage local | DR | Bunker |
|---|---|---:|---:|---|---|---|
| Bronze | `backup-tier=bronze` | 1/jour | 7 jours | DD-PROD | Non | Non |
| Silver | `backup-tier=silver` | 4/jour | 30 jours | DD-PROD | Option | Non |
| Gold | `backup-tier=gold` | 1 heure | 90 jours | DD-PROD | Oui | Non |
| Platinum | `backup-tier=platinum` | 1 heure | 90/180 jours | DD-PROD | Oui | **Oui** |

Cette matrice doit être considérée comme un modèle de départ.

Platinum est destiné aux workloads les plus critiques.

# 14. Rôle des SLP

Une **Storage Lifecycle Policy (SLP)** décrit les opérations de stockage appliquées aux images de sauvegarde.

Une SLP peut orchestrer notamment :

- la sauvegarde ;
- la duplication ;
- la réplication ;
- l'import ;
- le cycle de vie des copies.

Veritas décrit une SLP comme un ensemble d'instructions de stockage appliquées aux données sauvegardées ; plusieurs opérations permettent de créer plusieurs copies et NetBackup gère les opérations secondaires et leurs reprises.

Le rôle du SLP est donc différent de celui du Protection Plan.

### Protection Plan

Répond à la question :

> **Comment protéger ce workload Kubernetes ?**

### SLP

Répond à la question :

> **Comment gérer les copies de cette sauvegarde et leur cycle de vie ?**

# 17. AIR et site Bunker

Le site Bunker constitue un domaine NetBackup séparé.

```text
Production
-----------
NetBackup Primary PROD
Data Domain PROD

        |
        | AIR
        |
        v

Bunker
------
NetBackup Primary BUNKER
Data Domain BUNKER
```

AIR permet de répliquer les images entre domaines NetBackup et de créer automatiquement les informations de catalogue nécessaires dans le domaine cible. Veritas recommande AIR pour répliquer les sauvegardes entre domaines NetBackup.

---

# 18. Import SLP dans le Bunker

Pour une réplication AIR vers un domaine cible spécifique, le domaine cible doit disposer d'un **Import SLP**.

Le principe est :

```mermaid
flowchart LR

    subgraph PROD["Domaine NetBackup Production"]
        SLP["SLP source"]
        DD["DD-PROD"]
        REP["AIR / Replication"]
    end

    subgraph BUNKER["Domaine NetBackup Bunker"]
        IMPORT["Import SLP"]
        BDD["DD-BUNKER"]
    end

    SLP --> DD
    DD --> REP
    REP -. "AIR" .-> IMPORT
    IMPORT --> BDD
```

Pour une cible AIR spécifique, la documentation NetBackup indique que l'Import SLP doit être créé dans le domaine cible avant la configuration du SLP AIR source.

# 19. Fonctionnement avec une fenêtre réseau intermittente

Le Bunker n'est pas nécessairement connecté en permanence au réseau de production.

Le modèle cible est :

```mermaid
sequenceDiagram

    participant O as OpenShift
    participant N as NetBackup PROD
    participant D as DD-PROD
    participant F as Firewall
    participant B as NetBackup BUNKER
    participant DB as DD-BUNKER

    O->>N: Backup namespace
    N->>D: Création image

    Note over D,F: Réseau Bunker fermé

    D-->>D: Image conservée en attente AIR

    Note over F: Ouverture de la fenêtre AIR

    D->>F: Flux AIR
    F->>B: Réplication
    B->>DB: Import image

    Note over F: Fermeture de la fenêtre AIR

    D-->>D: Backup production continue
```

Le principe essentiel est que :

> **la sauvegarde primaire ne doit pas dépendre de la disponibilité du réseau Bunker.**

Le backup Kubernetes doit être disponible localement sur le stockage de production même lorsque le Bunker est inaccessible.

---

# 20. RPO Production et RPO Bunker

Les deux RPO doivent être considérés séparément.

Exemple :

```text
Backup Kubernetes :
    toutes les 1 heure

RPO Production :
    ≈ 1 heure
```

Si le réseau Bunker n'est ouvert que deux fois par jour :

```text
Fenêtre AIR :
    02:00 - 03:00
    14:00 - 15:00
```

le RPO Bunker sera différent du RPO de production.

Le Bunker constitue alors une protection complémentaire et non un stockage synchrone.

La conception finale doit donc définir explicitement :

- RPO Production ;
- RPO DR ;
- RPO Bunker ;
- durée maximale acceptable d'attente d'une réplication AIR.

# 22. Passage d'un niveau à un autre

Le modèle permet également de faire évoluer le niveau de protection d'un namespace.

Exemple initial :

```yaml

  backup-enabled: "true"
  backup-tier: "silver"
```

Le namespace est sélectionné par :

```text
IG-K8S-SILVER
```

Si l'application devient critique, le label peut évoluer vers :

```yaml
labels:
  backup-enabled: "true"
  backup-tier: "platinum"
```

Le namespace entre alors dans le périmètre de l'Intelligent Group Platinum.

Conceptuellement :


# 23. Namespace sans label

Une règle de gouvernance doit être définie pour les namespaces qui ne possèdent pas de label de sauvegarde.

Exemple :

```text
Namespace
    |
    +-- backup-enabled=true
    |       |
    |       +-- backup-tier=bronze/silver/gold/platinum
    |
    +-- aucun label
            |
            +-- hors périmètre
```

Il est recommandé de mettre en place un contrôle permettant d'identifier les namespaces non classifiés.

L'objectif est d'éviter qu'un namespace critique soit créé sans qu'une protection lui soit attribuée.

---

# 24. Gouvernance des niveaux

Les niveaux de protection ne devraient pas être librement choisis sans gouvernance.

Une matrice de responsabilité peut être définie :

| Niveau | Usage | Autorisation indicative |
|---|---|---|
| Bronze | Développement / workloads non critiques | Équipe applicative |
| Silver | Production standard | Équipe applicative / plateforme |
| Gold | Production critique | Équipe plateforme |
| Platinum | Criticité élevée / exigences Bunker | Équipe plateforme / Backup |

Cette gouvernance permet d'éviter une utilisation excessive du niveau Platinum et de maîtriser la capacité du stockage et des flux AIR.

# 25. Principes de conception à retenir

L'architecture cible repose sur les principes suivants.

### Principe 1 — Kubernetes exprime une intention

```text
backup-tier=gold
```

et non :

```text
backup-storage=DD01
```

### Principe 2 — Les Intelligent Groups font la sélection

Les labels Kubernetes permettent de construire des groupes dynamiques.

### Principe 3 — Les Protection Plans définissent le service

Ils définissent la fréquence, la planification et les paramètres de protection.

### Principe 4 — Les SLP gèrent les copies

Les SLP définissent les opérations de stockage et le cycle de vie des copies.

### Principe 5 — Le Bunker est indépendant

Le Bunker possède :

```text

+

```

### Principe 6 — AIR est asynchrone

Le backup de production ne doit pas attendre la disponibilité du Bunker.

### Principe 7 — Platinum bénéficie d'une copie isolée

Le niveau Platinum ajoute une copie AIR vers le Bunker.

# 27. Résumé du fonctionnement

Le fonctionnement complet peut être résumé en huit étapes :

1. Un namespace Kubernetes est créé.
2. Le namespace reçoit un label `backup-tier`.
3. NetBackup identifie le namespace via un Intelligent Group.
4. L'Intelligent Group est associé au Protection Plan correspondant.
5. Le Protection Plan déclenche automatiquement les sauvegardes.
6. Le SLP gère les copies et leur cycle de vie.
7. Pour Gold et Platinum, une copie supplémentaire peut être créée vers le site DR.
8. Pour Platinum, AIR transfère également les images vers le domaine NetBackup Bunker lorsque la fenêtre réseau est disponible.

```mermaid
flowchart LR

    A["Namespace"] --> B["Label"]
    B --> C["Intelligent Group"]
    C --> D["Protection Plan"]
    D --> E["Backup"]
    E --> F["SLP"]
    F --> G["DD Production"]

    F --> H["DR"]

    F --> I["AIR"]
    I --> J["NetBackup Bunker"]
    J --> K["DD Bunker"]
```

# 28. Conclusion

Le modèle proposé permet d'industrialiser la protection des namespaces Kubernetes/OpenShift avec NetBackup 11.2.

Le principe central est :

```text
LABEL KUBERNETES
       ↓
INTELLIGENT GROUP
       ↓
PROTECTION PLAN
       ↓
SLP
       ↓
COPIES DE SAUVEGARDE
       ↓
DD PROD / DR / BUNKER
```

Cette approche permet de conserver une séparation claire entre :

- les équipes Kubernetes, qui déclarent le niveau de protection ;
- les équipes NetBackup, qui définissent les politiques de sauvegarde ;
- l'infrastructure de stockage, qui fournit les destinations ;
- le site Bunker, qui fournit une copie isolée.

Le modèle **Bronze / Silver / Gold / Platinum** constitue ainsi un catalogue de services de sauvegarde utilisable par les équipes applicatives et OpenShift.

Le niveau **Platinum** complète cette architecture par une protection hors site via **AIR**, avec un domaine NetBackup indépendant et un Data Domain dédié au Bunker.

La prochaine étape de conception consistera à détailler le paramétrage NetBackup 11.2 : **Protection Plans, Intelligent Groups, SLP source, SLP Import Bunker, Storage Units/Data Domain, AIR, fenêtres de réplication et règles de rétention**, tout en conservant cette architecture cible.





# 9. Architecture DR et réplication

## 9.1 Objectif du site DR

Le site DR a pour objectif de permettre la continuité des opérations de sauvegarde et de restauration en cas d'indisponibilité du site de production.

Il faut distinguer deux objectifs :

1. **protéger les données sauvegardées** contre la perte du stockage de production ;
2. **permettre la reprise des services NetBackup** en cas de perte du Primary Server ou du site de production.

La réplication des données de sauvegarde et la réplication du catalogue NetBackup sont donc deux mécanismes différents.

---

# 9.2 Nombre de Primary Servers

Dans l'architecture cible, il est recommandé de disposer de :

```text
1 Primary Server dans le domaine Production
+
1 Primary Server dans le domaine DR
+
1 Primary Server dans le domaine Bunker
```

Soit :

```text
                    NETBACKUP
                       |
       +---------------+---------------+
       |               |               |
       v               v               v
 NBU PRIMARY       NBU PRIMARY      NBU PRIMARY
    PROD               DR             BUNKER
       |               |               |
       v               v               v
   DD-PROD           DD-DR          DD-BUNKER
```

Ces trois Primary Servers appartiennent à **trois domaines NetBackup distincts**.

Le domaine Bunker est destiné à l'isolation et à la résilience cyber/physique.

Le domaine DR est destiné à fournir une capacité de reprise opérationnelle.

---

# 9.3 Le rôle du Primary Server

Le Primary Server est le composant central du domaine NetBackup.

Il assure notamment :

- la gestion du catalogue ;
- la planification des sauvegardes ;
- la gestion des policies/Protection Plans ;
- la gestion des SLP ;
- la gestion des médias et des Storage Units ;
- la coordination des jobs ;
- la gestion des relations entre clients, Media Servers et stockage.

Le catalogue NetBackup réside sur le Primary Server. Il s'agit d'un élément essentiel de l'architecture de reprise.

Il faut donc éviter de considérer :

```text
réplication DD
```

comme équivalente à :

```text
réplication du catalogue NetBackup.
```

Ce sont deux mécanismes différents.

---

# 9.4 Le rôle du Media Server

Le Media Server est utilisé comme intermédiaire entre les clients et le stockage lorsque l'architecture le nécessite.

Dans notre architecture Kubernetes/OpenShift, le flux logique peut être représenté comme suit :

```mermaid
flowchart LR

    K8S["OpenShift / Kubernetes"]
    P["NetBackup Primary PROD"]
    M["NetBackup Media Server"]
    DD["Data Domain PROD"]

    K8S --> P
    P --> M
    M --> DD
```

Le Media Server assure notamment les fonctions de traitement du flux de sauvegarde et d'accès au stockage.

Les communications de contrôle et les informations de catalogue circulent entre le client, le Media Server et le Primary Server.

---

# 9.5 Media Server et Data Domain

Dans une architecture Data Domain, le Media Server peut être utilisé comme serveur de stockage/déduplication NetBackup selon la configuration retenue.

L'architecture logique devient alors :

```mermaid
flowchart LR

    K8S["Kubernetes / OpenShift"]
    P["Primary Server"]
    M["Media Server / Storage Server"]
    DD["Data Domain"]

    K8S -->|"Backup"| P
    P -->|"Job control"| M
    M -->|"Backup data"| DD
```

Il faut cependant distinguer :

- le **Primary Server** ;
- le **Media Server** ;
- le **Storage Server** ;
- le **Data Domain**.

Le Data Domain constitue la plateforme de stockage physique. NetBackup utilise les composants de stockage et les Storage Units pour gérer les destinations.

---

# 9.6 Architecture recommandée en Production

Pour une architecture importante, je recommande de ne pas faire reposer toute la charge sur le Primary Server.

Une architecture cible peut être :

```mermaid
flowchart TB

    subgraph PROD["SITE PRODUCTION"]

        K8S["OpenShift / Kubernetes"]

        P["NetBackup Primary PROD"]

        M1["Media Server 01"]
        M2["Media Server 02"]

        DD["Data Domain PROD"]

        K8S --> P

        P --> M1
        P --> M2

        M1 --> DD
        M2 --> DD
    end
```

Les Media Servers peuvent être utilisés pour :

- distribuer la charge ;
- fournir plusieurs chemins d'accès au stockage ;
- isoler les flux ;
- augmenter les performances ;
- améliorer la résilience du chemin de sauvegarde.

---

# 9.7 Architecture DR

Le site DR possède son propre domaine NetBackup.

```mermaid
flowchart TB

    subgraph PROD["SITE NOMINAL"]

        PP["Primary PROD"]
        M1["Media Server PROD 01"]
        M2["Media Server PROD 02"]
        DD1["Data Domain PROD"]

        PP --> M1
        PP --> M2
        M1 --> DD1
        M2 --> DD1
    end

    subgraph DR["SITE DR"]

        PD["Primary DR"]
        MD1["Media Server DR 01"]
        MD2["Media Server DR 02"]
        DD2["Data Domain DR"]

        PD --> MD1
        PD --> MD2
        MD1 --> DD2
        MD2 --> DD2
    end

    DD1 -. "Réplication / AIR selon design" .-> DD2
```

Le domaine DR est indépendant du domaine Production.

---

# 9.8 Attention : AIR ne réplique pas le Primary Server

AIR est destiné à la réplication des **images de sauvegarde** entre domaines NetBackup.

Il ne faut donc pas représenter le mécanisme comme :

```text
Primary PROD
      |
      | réplication
      v
Primary DR
```

mais plutôt comme :

```text
Data / images
      |
      v
Storage PROD
      |
      | AIR
      v
Storage DR
```

avec les catalogues correspondants gérés dans les domaines NetBackup concernés.

Le mécanisme AIR utilise un SLP dans le domaine source et un Import SLP dans le domaine cible.

---

# 9.9 Fonctionnement AIR

Le workflow AIR peut être représenté comme suit :

```mermaid
sequenceDiagram

    participant P as Primary PROD
    participant M as Media/Storage PROD
    participant DD1 as DD-PROD
    participant DD2 as DD-DR
    participant D as Primary DR

    P->>M: Backup job
    M->>DD1: Write backup image

    P->>M: SLP replication
    M->>DD2: AIR replication

    DD2->>D: Import event
    D->>D: Update target catalog
```

La documentation Veritas décrit le flux AIR avec un **Source Primary**, un **Source Media Server**, un **Target Primary** et un **Target Media Server/Storage Server**.

---

# 9.10 SLP côté Production

Dans le domaine Production, le SLP définit le cycle de vie de l'image.

Exemple conceptuel :

```text
SLP-K8S-GOLD

    Backup
       |
       v
    DD-PROD
       |
       v
    Replication
       |
       v
    DD-DR
```

Le SLP orchestre donc la création de la copie primaire et les opérations secondaires.

Les SLP permettent notamment de définir les opérations de stockage et les destinations associées.

---

# 9.11 SLP d'import côté DR

Dans le domaine DR, un Import SLP est défini.

```text
Domaine PROD

SLP-K8S-GOLD
       |
       | AIR
       v

Domaine DR

SLP-IMPORT-K8S-GOLD
       |
       v
DD-DR
```

Pour une configuration AIR ciblée, Veritas documente la création d'un SLP avec l'opération **Import** dans le domaine cible.

---

# 9.12 Architecture complète Nominal / DR

L'architecture peut donc être représentée comme suit :

```mermaid
flowchart LR

    subgraph NOMINAL["SITE NOMINAL"]

        K8S["OpenShift / Kubernetes"]

        P1["Primary PROD"]

        M11["Media Server PROD 01"]
        M12["Media Server PROD 02"]

        DD1["Data Domain PROD"]

        K8S --> P1

        P1 --> M11
        P1 --> M12

        M11 --> DD1
        M12 --> DD1

        SLP1["SLP PROD"]
        P1 --> SLP1
        SLP1 --> DD1
    end

    subgraph DR["SITE DR"]

        P2["Primary DR"]

        M21["Media Server DR 01"]
        M22["Media Server DR 02"]

        DD2["Data Domain DR"]

        ISLP["Import SLP"]

        P2 --> M21
        P2 --> M22

        M21 --> DD2
        M22 --> DD2

        ISLP --> DD2
    end

    DD1 -. "AIR" .-> DD2
    DD2 -. "Import event" .-> P2
```

---

# 9.13 Quel est le rôle du Primary DR ?

Le Primary DR ne doit pas être considéré comme une copie passive du Primary PROD.

Il constitue un **domaine NetBackup capable de gérer les images répliquées sur le site DR**.

Son rôle est notamment de :

- posséder le catalogue du domaine DR ;
- recevoir les événements AIR ;
- connaître les images importées ;
- permettre la restauration des images présentes sur DD-DR ;
- fournir les services NetBackup nécessaires à l'exploitation DR.

L'objectif est donc de pouvoir restaurer les données depuis le site DR même si le domaine Production est indisponible.

---

# 9.14 DR des données vs DR du Primary

Deux scénarios doivent être distingués.

### Scénario A — perte du stockage Production

```text
DD-PROD
   X
   |
   v
DD-DR
   |
   v
Primary DR
   |
   v
Restore
```

Les copies présentes sur le domaine DR permettent de restaurer les données.

### Scénario B — perte du Primary PROD

Le catalogue du domaine Production doit également être protégé.

Il faut donc prévoir une **stratégie de sauvegarde et de récupération du catalogue NetBackup**.

La protection du catalogue doit être traitée séparément de la réplication des images de sauvegarde.

---

# 9.15 Protection du catalogue NetBackup

Le catalogue NetBackup contient les informations nécessaires à la connaissance des sauvegardes.

Il doit donc faire l'objet d'une stratégie de protection spécifique.

Conceptuellement :

```mermaid
flowchart LR

    P["Primary PROD"]
    CAT["Catalogue NetBackup"]
    CB["Catalog Backup"]
    CST["Stockage protégé"]

    P --> CAT
    CAT --> CB
    CB --> CST
```

La perte du Primary Server ne signifie donc pas nécessairement la perte des données sauvegardées, mais la capacité à exploiter ces données dépend de la disponibilité du catalogue ou du mécanisme de reprise approprié.

La procédure de récupération d'un Primary Server utilise notamment le **disaster recovery package** pour restaurer l'identité et la configuration nécessaires avant la récupération du catalogue.

---

# 9.16 Nombre recommandé de Media Servers

Le nombre de Media Servers dépend de la volumétrie, des performances nécessaires, des flux réseau et du niveau de résilience recherché.

Pour une architecture de référence, je recommande :

### Production

```text
1 Primary Server
2 Media Servers
1 Data Domain
```

soit :

```mermaid
flowchart LR

    P["Primary PROD"]

    M1["Media 01"]
    M2["Media 02"]

    DD["Data Domain PROD"]

    P --> M1
    P --> M2

    M1 --> DD
    M2 --> DD
```

### DR

```text
1 Primary DR
2 Media Servers
1 Data Domain DR
```

### Bunker

Pour le Bunker :

```text
1 Primary Bunker
1 ou 2 Media Servers selon volumétrie
1 Data Domain Bunker
```

Le nombre exact doit être dimensionné à partir de la volumétrie et des débits attendus.

---

# 9.17 Media Servers et résilience

Le Media Server n'est pas le composant qui porte le catalogue NetBackup.

Il fournit principalement le chemin d'accès aux données.

Ainsi :

```text
Media Server 01 DOWN
        |
        v
Media Server 02
        |
        v
Data Domain
```

peut permettre de maintenir la capacité de sauvegarde/restauration si l'architecture et les Storage Units sont correctement configurés.

NetBackup dispose également de mécanismes permettant aux jobs résilients de continuer pendant certaines interruptions de communication avec le Primary Server.

---

# 9.18 Data Domain et réplication

Dans l'architecture cible, le Data Domain est le support de stockage des images.

Le schéma devient :

```mermaid
flowchart LR

    subgraph PROD["Production"]
        M["Media Servers"]
        DD1["DD-PROD"]
    end

    subgraph DR["DR"]
        M2["Media Servers"]
        DD2["DD-DR"]
    end

    M --> DD1
    DD2 --> M2

    DD1 -. "Réplication / AIR" .-> DD2
```

La réplication doit être conçue avec NetBackup/AIR et les capacités de réplication supportées par la plateforme de stockage.

La documentation NetBackup indique notamment que la réplication pour les Storage Servers de type MSDP est supportée via les mécanismes de réplication prévus par NetBackup.

---

# 9.19 DR et Bunker : deux objectifs différents

Le site DR et le site Bunker ne doivent pas être considérés comme deux copies identiques.

### DR

Objectif :

> **continuité opérationnelle et restauration rapide**

Le site DR peut donc disposer de :

```text
Primary DR
+
Media Servers
+
Data Domain DR
```

avec une connectivité relativement permanente avec la production.

### Bunker

Objectif :

> **protection isolée contre une compromission ou une destruction du domaine de production**

Le site Bunker dispose de :

```text
Primary Bunker
+
Media Server(s)
+
Data Domain Bunker
```

et la connectivité est ouverte uniquement pendant les fenêtres AIR.

# 9.21 Synthèse des composants

| Site | Primary | Media Servers | Stockage | Fonction |
|---|---:|---:|---|---|
| Nominal | 1 | 2 recommandés | DD-PROD | Sauvegarde primaire |
| DR | 1 | 2 recommandés | DD-DR | Reprise / restauration |
| Bunker | 1 | 1 à 2 | DD-BUNKER | Copie isolée |

Cette architecture conduit donc à **3 Primary Servers**, chacun appartenant à son propre domaine NetBackup.

Le nombre de Media Servers est une décision de dimensionnement. Deux Media Servers en production et en DR constituent une architecture de référence permettant de répartir les flux et de disposer d'une redondance du chemin d'accès au stockage.

---

# 9.22 Flux de données

Il est important de distinguer les différents flux.

```mermaid
flowchart LR

    K8S["Kubernetes"]

    P["Primary"]
    M["Media Server"]
    DD["Data Domain"]

    AIR["AIR"]

    DRP["Primary DR"]
    DRDD["Data Domain DR"]

    K8S -->|"Données backup"| M
    M -->|"Écriture"| DD

    P -->|"Contrôle / catalogue"| M

    DD -->|"Réplication AIR"| AIR
    AIR --> DRDD

    AIR -->|"Import event"| DRP
```

Les données de sauvegarde ne transitent donc pas nécessairement par le Primary Server.

Le Primary coordonne les opérations ; le Media Server assure le traitement des données et l'accès au stockage.

---

# 9.23 Principe de dimensionnement

Le dimensionnement des Media Servers doit être réalisé en fonction de :

- nombre de namespaces ;
- nombre de clusters OpenShift ;
- volumétrie totale ;
- taux de changement ;
- fenêtre de sauvegarde ;
- RPO ;
- débit réseau ;
- performances Data Domain ;
- nombre de jobs simultanés ;
- trafic de duplication/AIR ;
- trafic de restauration attendu.

Le nombre de Media Servers ne doit donc pas être déterminé uniquement par le nombre de clusters Kubernetes.

# 9.25 Principe de résilience

La résilience repose donc sur plusieurs niveaux indépendants :

```text
Niveau 1
--------
Redondance Media Servers

Niveau 2
--------
Data Domain Production

Niveau 3
--------
Copie DR

Niveau 4
--------
Primary DR + Media Servers DR

Niveau 5
--------
Copie Bunker via AIR

Niveau 6
--------
Primary Bunker indépendant
```

Cette architecture permet de traiter séparément :

- panne d'un Media Server ;
- panne du stockage local ;
- perte du site nominal ;
- perte du Primary Production ;
- incident majeur affectant le domaine NetBackup Production ;
- scénario de compromission nécessitant une copie isolée.

---

# 9.26 Point important : DR du catalogue

La réplication AIR ne doit pas être considérée comme une réplication du catalogue du Primary Production.

La stratégie DR doit donc comporter deux volets :

```text
1. Protection des données
   Backup → SLP → AIR → DD-DR

2. Protection du catalogue
   Catalog Backup → stockage dédié/protégé
```

La procédure de Disaster Recovery du Primary devra être documentée séparément.

Cette distinction est essentielle pour garantir qu'une restauration complète du service NetBackup puisse être réalisée après la perte du Primary Server.

---

# 9.27 Résumé

L'architecture cible proposée repose sur :

```text
3 domaines NetBackup

Production
    |
    +-- 1 Primary
    +-- 2 Media Servers
    +-- DD-PROD

DR
    |
    +-- 1 Primary
    +-- 2 Media Servers
    +-- DD-DR

Bunker
    |
    +-- 1 Primary
    +-- 1/2 Media Servers
    +-- DD-BUNKER
```

Les sauvegardes Kubernetes sont réalisées dans le domaine Production.

Les SLP orchestrent les copies.

AIR permet de transférer les images vers le domaine DR et/ou Bunker selon le niveau de protection.

Le Primary DR permet d'exploiter les images présentes sur le stockage DR.

Le Primary Bunker constitue un domaine NetBackup indépendant destiné à conserver une copie isolée.

La protection du **catalogue NetBackup** est traitée séparément de la réplication des images.

Cette séparation permet d'obtenir une architecture cohérente entre :

```text
Protection Kubernetes
        +
Stockage
        +
DR
        +
Bunker
        +
Disaster Recovery NetBackup
```
